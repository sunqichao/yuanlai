# 07 点对点网络协议

本章定义节点间的 TCP 线协议。P2P 消息不属于共识编码；接收端仍必须独立验证区块头、工作量、区块正文和所有状态转换。

## 1. 帧格式

每帧为：

```
magic[4] ‖ payload_len:u32_le ‖ payload[payload_len]
```

- `magic` 固定为 ASCII `YLP2`。
- `payload` 第一个字节是消息 tag，后续字段按 [01-serialization.md](01-serialization.md) 编码。
- `payload_len` 必须至少为 1，且不得超过 `MAX_BLOCK_SIZE + 1` 字节；该上限允许一个达到共识大小上限的 Block 消息连同 tag。
- 一个帧解码必须消费全部 `payload`。长度不符、未知 tag、截断字段、超限 payload 或帧后多余字节均为协议错误，接收方必须关闭连接。
- TCP 字节流中的帧连续拼接，不得在帧之间插入分隔符。接收方必须先读满 8 字节帧头、检查长度上限，再分配并读取 payload。

该固定 magic 不区分网络；网络由握手中的 `chain_id` 区分。P2P 帧不添加校验和，区块内容由共识哈希和工作量验证。

## 2. 消息编码

整数均为小端序。Hash 为 32 字节。以下表格中，列表使用 `BoundedVec` 编码（`u32` 个数加元素），Block 与 BlockHeader 使用规范区块编码。

| Tag | 消息 | 字段（tag 后） |
|---:|---|---|
| `0x00` | `Version` | `protocol_version:u32`、`chain_id:Hash`、`best_height:Height`、`best_id:Hash`、`nonce:u64` |
| `0x01` | `Verack` | 无 |
| `0x02` | `GetHeaders` | `locator:List<Hash,32>`、`stop:Hash` |
| `0x03` | `Headers` | `headers:List<BlockHeader,2000>` |
| `0x04` | `GetBlock` | `block_id:Hash` |
| `0x05` | `Block` | `block:Block` |
| `0x06` | `Ping` | `nonce:u64` |
| `0x07` | `Pong` | `nonce:u64` |
| `0x08` | `NotFound` | `block_id:Hash` |
| `0x09` | `Transaction` | `tx:Tx` |
| `0x0a` | `TransactionAck` | `txid:Hash`、`accepted:bool` |

空 locator 表示从创世区块开始请求。非空 locator 按最近到最旧排列。零 `stop` 表示不指定停止点。

## 3. 握手

连接建立后，双方都必须先发送一个 `Version`。`protocol_version` 必须为 1，`chain_id` 必须与本地网络一致，`nonce` 必须非零。节点发现对端 nonce 与本地连接 nonce 相同，或对端 chain ID/版本不匹配时，必须关闭连接。

双方收到有效 `Version` 后各发送一个 `Verack`。只有双方均收到对方 `Verack` 后，才可发送或处理同步及 liveness 消息。握手中再次收到 `Version` 或 `Verack` 为协议错误。`best_height` 和 `best_id` 是提示，不是可信状态，也不能代替头链验证。

## 4. Header 同步

请求方发送 `GetHeaders`。响应方在 locator 中选择其活动链上第一个匹配的 ID，并按链顺序发送其后的 header，最多 2000 个；若 locator 为空或没有匹配项，则从创世之后开始。若非零 `stop` 出现在返回链上，响应必须在该 header 处停止。没有更多 header 时返回空 `Headers`。

接收方必须按顺序将 header 插入本地 `HeaderTree`，执行全部 BLK-02 至 BLK-08 验证，并按累计工作选择活动头链。仅凭 `Version.best_height`、`Version.best_id` 或未验证 headers 不得切换活动区块状态。

## 5. Block 获取与验证

`GetBlock` 请求指定 ID 的活动链区块正文。若本地没有该 ID，响应 `NotFound`；否则响应对应 `Block`。接收方必须验证 Block header 与已知 header 完全一致，并对新活动分支执行完整区块和状态转换校验。分叉切换必须按 FORK-03 回滚到共同祖先，再应用新分支；任何一个区块验证失败都不得部分提交切换。

节点可以因本地策略限速或断开过量请求的 peer，但不得把 peer 提供的数据视为已验证状态。失联、超时和未实现消息不是共识错误，也不得影响已验证的活动链。

本仓库的 `--listen` 实现最多并行服务 8 个入站 peer，且每个源 IP 最多占用 2 个 slot；达到任一上限后新连接会被关闭。IPv4-mapped IPv6 地址按对应 IPv4 地址计数。握手总时限为 5 秒，握手后每帧读取总时限为 60 秒。每个 outbound peer 对解析出的 socket 地址共用 5 秒连接 deadline；系统 hostname 解析不受该 socket deadline 控制。以上均为节点本地资源策略，不属于共识规则。可重复指定 `--connect ADDR` 配置静态 peer；节点按顺序尝试所有地址，至少一个同步成功则命令成功，交易文件会逐一提交给各 peer。`--stay-connected` 会把 CLI 地址合并写入 datadir 的 `peers.txt`，重启时可只传 `--stay-connected` 加载已保存地址；地址总数上限为 64。该模式为每个 peer 独立记录失败退避和最近成功时间，失败时按 1–30 秒指数退避，成功后 30 秒再次同步。peer 仍按顺序通过短连接访问，不使用常驻 socket，也不并行同步或自动发现 peer。

## 6. Liveness

`Ping(nonce)` 必须以相同 nonce 的 `Pong(nonce)` 响应。Ping/Pong 不携带链状态。连续未响应的连接可由本地策略关闭。

## 7. 用户交易传播（实现中）

`Transaction` 携带一笔规范编码交易。发送方不得发送 `Coinbase`、`Expire` 或 `AutoCancel` 等系统交易。接收方必须先按当前活动链和本地 mempool 顺序完整验证交易；无效或重复交易不得继续转发。只有新接纳的交易才可以向其他已握手 peer 转发，且不得回传给来源 peer。

接收方必须以 `TransactionAck` 回应，`txid` 必须与请求交易 ID 相同；`accepted` 为真表示交易通过验证并已接纳，或此前已在池中。

当前 node 的 `--listen --beneficiary PUBKEY` 会按该受益人的候选区块上下文验证交易；`--connect --tx-file PATH` 在同步后提交交易并等待匹配 txid 的 ACK。新接纳的交易会原子写入 datadir 的 `mempool.dat`，再转发给来源以外、当前已握手的入站 peer，单 listener 最多 8 个连接。启动 listener 或矿工时，节点会按当前活动链重新验证并丢弃过期/无效条目。network mode 当前不能同时挖矿，也不提供持久 peer 连接或自动发现；停止 relay 后可使用相同 datadir 重新启动矿工消费待处理交易。
